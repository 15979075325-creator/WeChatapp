# 三人开发路线

交付目标：在手机微信里，从发牌开始完成一局对战，能使用功能牌、看到胜负、再开一局。三个新增功能的优先顺序是 **战绩保存 → 电脑难度 → 出牌动画**。

| 成员 | 分支 | 负责范围 | 做完怎样验收 |
| --- | --- | --- | --- |
| A：牌桌 | `feat/table-ui` | 修改 `game.js`。优化可出牌高亮、翻页和触控；把难度、战绩按钮接到牌桌。 | 7 张牌都能翻到；点击可出的牌后桌面和手牌更新；换色弹窗能取消。 |
| B：电脑与规则 | `feat/cpu-levels` | 修改 `rules.js`。简单档随机出合法牌；普通档延续当前的功能牌和颜色偏好。 | 两档都只出合法牌；跳过和罚抽后回合正确；牌库用完还能继续；任一方出完即结算。 |
| C：战绩与验收 | `feat/local-stats` | 新增 `stats.js`，保存胜、负、平和最近 5 局；提供战绩界面需要的数据；整理真机验收结果。 | 每局只记一次；退出后重新打开仍能看到战绩；手动重新发牌不会被记为输。 |

## 第一天：统一基线

三个人从 `main` 导入同一版本，各打一局。确认玩法、验收标准和接口，再各自开分支。先按下面的接口开发，减少多人同时改入口文件：

- B 保持 `cpuMove(game)` 仍可调用，新增可选参数 `cpuMove(game, difficulty)`，难度值用 `easy` 和 `normal`。A 负责传参。
- C 提供 `loadStats()` 和 `recordResult(winner)`；`winner` 只接收 `player`、`cpu`、`tie`。返回累计胜负平和最近 5 局。A 在正式结算时调用一次，并接战绩弹窗。

## 第二天：开发和合并

每个人先在自己的分支验证，再开 Pull Request。优先合并规则和战绩模块，再合并牌桌接线。由 A 统一合并入口文件；每次合并后编译一局。

## 第三天：手机验收和演示

1. 真机扫码，确认看到《课间牌局》，且手牌点得到、翻得动。
2. 测试普通牌、跳过、罚抽和换色；没有可出牌时能摸一张。
3. 打完一局，检查胜负、再来一局、比分和本地战绩。关闭小游戏再打开，确认战绩仍在。
4. 彩排：A 出一张牌或换色，B 讲电脑怎样选牌，C 展示结算和战绩。时间不够就把动画留到下一版。

正式演示前先准备一场方便展示功能牌的对局，避免现场等到碰巧发出某张牌。
